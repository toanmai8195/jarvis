# Handbook — P0-T04: GitHub Actions chạy theo đường dẫn thay đổi (`com/tm/server/**` → golangci-lint + `bazel test` target bị ảnh hưởng; `com/tm/app/**` → pnpm lint/test/build package bị ảnh hưởng)

## Một workflow: job `changes` + `if`, không lọc bằng `paths:`
- **Chủ đề**: `ci/github-actions`
- **Bối cảnh**: DoD cần "sửa `com/tm/app` không kích hoạt `bazel test` và ngược lại", và sau này job CI sẽ thành required check của nhánh `main`.
- **Cách làm & lý do**:
  - Một file `ci.yml`, trigger `pull_request` vào `main` + `push` lên `main`. Job `changes` luôn chạy và ghi `server=true|false`, `app=true|false`, `base` vào `$GITHUB_OUTPUT`. Job `server`/`app` có `needs: changes` và `if: needs.changes.outputs.<vùng> == 'true'`.
  - Không dùng `on.<event>.paths`: workflow bị lọc thì **không có check run nào**, và required check treo "Expected — Waiting" mãi. Job bị bỏ qua do `if` hiện "skipped", GitHub coi là đạt.
  - Cũng không dùng action có sẵn như `dorny/paths-filter`: logic nằm trong `scripts/ci-changes.sh` để **chạy được trên máy dev** (execute-all không push trong task, không có `act`), và test được bằng bash test.
  - File của chính CI (`.github/workflows/**`, `scripts/ci-*`) đổi thì chạy cả hai job, để thay đổi CI luôn được chạy thử.
- **Bẫy / lưu ý**:
  - Base của diff khác nhau theo sự kiện. PR: `origin/${{ github.base_ref }}`. Push lên `main`: `github.event.before`. Nếu dùng `origin/main` cho push thì sau checkout `origin/main` **chính là** HEAD, diff rỗng, CI trên `main` không chạy gì mà vẫn xanh. `before` = 40 số `0` (tạo nhánh) hoặc commit không còn (force push) → chạy tất cả.
  - Diff tính từ **merge-base** (`git merge-base BASE HEAD`, tương đương `BASE...HEAD`). Nếu diff thẳng `BASE HEAD` thì commit mới trên `main` sau điểm tách nhánh bị tính nhầm là thay đổi của PR.
  - `git diff --name-only` mặc định bật phát hiện đổi tên và chỉ in **tên mới**: file chuyển từ `com/tm/app/...` sang `com/tm/docs/...` sẽ không kích hoạt job app. Dùng `--no-renames`.
  - So tiền tố có `/` (`com/tm/server/*`): `com/tm/serverx/` không bị khớp nhầm.
  - Mọi job có checkout đều cần `fetch-depth: 0`, không chỉ job `changes`: job `server`/`app` cũng tự diff lại (tính target, filter pnpm).
  - Giá trị `${{ ... }}` truyền vào `run:` qua `env:` rồi dùng `"$BASE"`, không nhúng thẳng vào script (tránh injection từ tên nhánh).

## Target Bazel bị ảnh hưởng bằng `bazel query rdeps` (G14)
- **Chủ đề**: `bazel`, `bazel/query`, `ci`
- **Bối cảnh**: CI chỉ test target phụ thuộc vào file đổi. Các công cụ có sẵn: `bazel-diff` (so hash target giữa hai commit, phải build JVM tool và chạy query hai lần trên hai checkout), `target-determinator` (tương tự, cần checkout commit base). Repo mới có vài package.
- **Cách làm & lý do**:
  - Chọn `bazel query` thuần trên HEAD, không cần công cụ thêm:
    1. File đổi → label ứng viên. File còn tồn tại → `//<pkg>:<đường dẫn trong pkg>`, với `pkg` là thư mục gần nhất có `BUILD.bazel`. File `BUILD` đổi hoặc file bị xoá → `//<pkg>:all` của package gần nhất **còn tồn tại**.
    2. `bazel query --keep_going 'set(...)'` giữ ứng viên là target thật. `db/**/*.sql` nằm trong package gốc nhưng không được khai báo, nên bị loại ở đây.
    3. `tests(rdeps(//..., set(...))) except attr(tags, manual, //...)`. `tests()` mở `test_suite` ra thành từng test (vd `com_tm_container_test` → `..._test_1`, `..._test_2`).
  - File toàn cục (`MODULE.bazel`, `MODULE.bazel.lock`, `go.mod`, `go.sum`, `.bazelrc`, `.bazelversion`, `BUILD.bazel` gốc) và mọi `*.bzl` → in `//...`. Với `.bzl` có thể tính bằng `rbuildfiles`, nhưng macro dùng chung thì gần như mọi package đều load, nên `//...` đơn giản mà vẫn đúng.
  - Không có target nào → `ci-server.sh` bỏ qua `bazel test` và in lý do.
  - Đổi lại, cách này có giới hạn: nó chỉ nhìn **đồ thị trên HEAD**. Thay đổi làm **mất** một cạnh phụ thuộc vẫn đúng, vì chính file BUILD của package phụ thuộc đổi nên package đó được chọn. Nhưng thay đổi ngoài đồ thị (ví dụ file đọc qua `data` bằng glob) thì chỉ đúng khi glob khai báo file đó. Khi repo lớn, hoặc cần xét cả thay đổi ở external repo, chuyển sang `bazel-diff`.
- **Bẫy / lưu ý**:
  - `bazel test` với danh sách rỗng báo `No test targets were found` (exit 4). `bazel test` không kèm target báo `no targets specified`. Phải kiểm rỗng trước khi gọi.
  - Package bị xoá hẳn: query label của nó báo `no such package`. `--keep_going` trả exit **3** (kết quả một phần), phải chấp nhận 3 ở bước lọc. Bước rdeps **không** dùng `--keep_going`, để lỗi BUILD thật (cú pháp, dep sai) làm job fail thay vì bị nuốt.
  - Nhiều file xoá cùng package sinh cùng `//<pkg>:all` → bỏ trùng trước khi truy vấn.
  - Log tiến trình của Bazel ra stderr, còn label ra stdout. Script chỉ đọc stdout.
  - Bash 3.2 của macOS: không có `mapfile`, và `"${arr[@]}"` rỗng dưới `set -u` là lỗi "unbound variable". Nên kiểm `${#arr[@]}` trước khi mở rộng mảng. Biến vòng lặp `for f` trong hàm phải `local f`, nếu không sẽ ghi đè biến cùng tên của hàm gọi (bug đã gặp trong test).
- **Code**: [ci-affected.sh#L29-L80 — is_global_file, package_of, candidate_label, query_set](../../../../../../scripts/ci-affected.sh#L29-L80), [ci-affected.sh#L82-L146 — main](../../../../../../scripts/ci-affected.sh#L82-L146), [ci-server.sh#L16-L40 — main](../../../../../../scripts/ci-server.sh#L16-L40)
- **Tham khảo**: [Bazel query reference — rdeps, tests, set](https://bazel.build/query/language), [bazel-diff](https://github.com/Tinder/bazel-diff), [target-determinator](https://github.com/bazel-contrib/target-determinator)

## Job app: install frozen, filter theo merge-base, chạy tất cả khi file gốc workspace đổi
- **Chủ đề**: `node/pnpm`, `ci`
- **Bối cảnh**: P0-T01b đã chỉ ra ba vấn đề: (1) `pnpm ... lint test build` chỉ chạy `lint`. (2) pnpm 11 tự `install` không frozen trước `run`. (3) Filter `!snaptix-app` làm CI không chạy package nào khi chỉ file gốc workspace đổi.
- **Cách làm & lý do**:
  - `pnpm install --frozen-lockfile` chạy trước: lockfile lệch thì fail ngay với `ERR_PNPM_OUTDATED_LOCKFILE`, không script nào chạy.
  - Lệnh đúng của project-structure: `pnpm --filter "...[<merge-base>]" --filter '!snaptix-app' --if-present run '/^(lint|test|build)$/'`. Truyền SHA merge-base thay cho `origin/main`, để cùng một lệnh dùng được cho cả PR lẫn push (`before`).
  - `package.json` gốc, `pnpm-workspace.yaml`, `pnpm-lock.yaml` hoặc file CI đổi → `pnpm --recursive --filter '!snaptix-app' --if-present run ...`. Chỉ có một filter phủ định nghĩa là "mọi package trừ root", nên script gốc không tự gọi đệ quy lại cả workspace.
  - Chạy xong thì `git diff --exit-code -- pnpm-lock.yaml`, chốt chặn cuối nếu có gì đó viết lại lockfile.
  - Toolchain lấy từ nguồn sự thật. `pnpm/action-setup` với `package_json_file: com/tm/app/package.json` đọc `packageManager`. `setup-node` với `node-version-file` cùng file đọc `engines.node`. Không ghi số phiên bản thứ hai trong workflow.
- **Bẫy / lưu ý**:
  - Khi chỉ một package được chọn, pnpm in output **không có tiền tố** `<pkg> <script>:`. Test đếm dòng phải khớp cả hai dạng.
  - Workspace chưa có package (hiện tại): filter in `No projects matched the filters`, exit 0. CI trên `main` vẫn xanh.
  - Script regex chạy `lint`/`test`/`build` **song song** trong một package: một script fail thì các script khác có thể đã chạy xong. Exit code vẫn khác 0 (`ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL`).
- **Code**: [ci-app.sh#L27-L66 — run_all, main](../../../../../../scripts/ci-app.sh#L27-L66), [ci.yml#L102-L129 — job app](../../../../../../.github/workflows/ci.yml#L102-L129)

## golangci-lint v2: pin bản, preset `standard`, không bật `std-error-handling`
- **Chủ đề**: `go/lint`, `ci`
- **Bối cảnh**: Cần lint Go trong CI với phiên bản cố định. Máy dev có golangci-lint 2.14.0 (bản mới nhất, build bằng go1.27.1, cùng Go của module).
- **Cách làm & lý do**:
  - `com/tm/server/.golangci.yml`: `version: "2"`, `linters.default: standard` (errcheck, govet, ineffassign, staticcheck, unused), formatter `gofmt`. Không ghi `run.go`, vì golangci-lint đọc Go version từ `go.mod`.
  - Không bật preset exclusion `std-error-handling`: preset này bỏ qua lỗi không kiểm của `os.Remove`, `Close`... Dự án tiền/booking muốn mọi lỗi đều được xử lý, hoặc bỏ qua có chủ đích bằng `_ =`.
  - Trong CI dùng `golangci/golangci-lint-action` với `install-only: true` + `version: v2.14.0` để cài binary chính thức, còn lệnh chạy nằm trong `scripts/ci-server.sh`. Như vậy chạy lint trên máy dev giống hệt CI. Cần `actions/setup-go` với `go-version-file: com/tm/server/go.mod`: golangci-lint gọi toolchain Go để load package.
  - Action pin bằng **full commit SHA** kèm comment tag (`@3d3c42e… # v7.0.1`). Tag có thể bị dời, SHA thì không. `bazel-contrib/setup-bazel` dùng tag không có `v` (`0.19.0`), nên càng phải pin SHA.
- **Bẫy / lưu ý**:
  - Lint chạy trên `./...` không quét vào symlink `bazel-*`, vì Go package pattern không đi theo symlink.
  - Lấy SHA của tag: `git ls-remote https://github.com/<repo> 'refs/tags/<tag>' 'refs/tags/<tag>^{}'`. Với annotated tag thì dòng `^{}` mới là commit, dòng không có `^{}` là object tag.
  - Fixture sửa bằng cách nối `// tc` ngay sau một hàm viết trên một dòng sẽ bị `gofmt` báo lỗi. Muốn lint pass thì sửa nội dung comment có sẵn.
- **Code**: [.golangci.yml — cấu hình](../../../../server/.golangci.yml), [ci.yml#L66-L100 — job server](../../../../../../.github/workflows/ci.yml#L66-L100)
- **Tham khảo**: [golangci-lint configuration v2](https://golangci-lint.run/docs/configuration/file/), [GitHub — using third-party actions (pin SHA)](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions#using-third-party-actions)

## Test script CI bằng binary giả qua biến môi trường
- **Chủ đề**: `bash`, `testing`, `ci`
- **Bối cảnh**: Script CI gọi Bazel, pnpm, golangci-lint. Chạy thật thì chậm, và khó tạo lỗi có chủ đích (exit 3 của `--keep_going`, lockfile bị viết lại).
- **Cách làm & lý do**:
  - Mỗi script đọc công cụ qua biến (`BAZEL`, `PNPM`, `GOLANGCI_LINT`, mặc định là tên lệnh thật). Test viết một script giả vào thư mục tạm. Script giả ghi lại argv và trả output/exit code điều khiển bằng `FAKE_*`.
  - Mỗi ca dựng một repo git mới trong `mktemp -d` với commit `base` + commit thay đổi, rồi so stdout, exit code và log lời gọi. Log được nối thành một dòng, nên pattern kiểm được cả **thứ tự** (lint trước bazel, install trước run).
  - Hành vi với công cụ thật được kiểm ở test case của task (TC08–TC24) trên clone tạm có fixture `pkg/tca..tcc`, `tc-a..tc-c`.
- **Bẫy / lưu ý**: Hook của repo chặn lệnh Bash có chuỗi `git commit` không kèm Task ID, kể cả trong clone tạm. Commit fixture nằm trong hàm của file test/env, không gõ trực tiếp trong lệnh.
