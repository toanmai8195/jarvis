# Handbook — P0-T10a: Image OCI cho core (`cmd/server`, `cmd/worker`) bằng macro `com_tm_go_image`

## Tên image tách khỏi tên target: attr `image` trên macro, Gazelle giữ nguyên
- **Chủ đề**: `bazel/macro`, `bazel/gazelle`, `docker`
- **Bối cảnh**: Gazelle đặt tên binary theo thư mục, nên `services/core/cmd/server` → target `server`, tag mặc định `com.tm.go.server:v1.0.0`. Tag này không nói service nào, và `services/stats-worker/cmd/worker` sau này cũng ra `com.tm.go.worker` → trùng tag với `services/core/cmd/worker`.
- **Cách làm & lý do**: Thêm tham số `image` vào `com_tm_go_image`; macro tự tiêu thụ (không đẩy xuống `**kwargs` của `go_binary`) và chỉ dùng cho `repo_tags` của `oci_load`: `image_tag(name, tag, image)` → `com.tm.go.<image hoặc name>:<tag>`. BUILD của core ghi `image = "core-server"` / `image = "core-worker"`. Tên target (`server_docker`) và entrypoint (`/app/server`) vẫn theo `name`, nên lệnh và đường dẫn trong docs không đổi. Gazelle chỉ merge các attr mà nó sinh (`embed`, `srcs`, `deps`, `visibility`...), attr lạ trên rule đã có được giữ → `bazel run //:gazelle -- -mode=diff` vẫn exit 0, không cần `# keep`. Lời gọi không truyền `image` (`tools/smoke`) giữ `com.tm.go.smoke:v1.0.0`. Phương án bị loại: đổi `name` bằng `# keep` (đổi luôn tên target, entrypoint và dễ lệch với Gazelle); `map_kind` riêng theo thư mục (không có cơ chế đó).
- **Bẫy / lưu ý**: `image = ""` cũng phải rơi về `name` (`image or name`) — có test skylib cho cả `None` và chuỗi rỗng. Mọi `*.bzl` là file toàn cục với CI (`ci-affected.sh` → `//...`), nên sửa macro kéo theo test toàn bộ.

## `tar` của tar.bzl mặc định đóng gói runfiles: tắt để layer chỉ còn binary
- **Chủ đề**: `bazel/rules_oci`, `bazel/tar`, `docker`
- **Bối cảnh**: Layer binary của smoke là 3152896 byte với binary 1573024 byte — gấp đôi. `tar -tvf` trên layer cho thấy cả `app/smoke` lẫn `app/smoke.runfiles/_main/tools/smoke/smoke_/smoke`. Với binary core ~20 MiB, image sẽ phình thêm ~20 MiB vô ích.
- **Cách làm & lý do**: Macro `tar(...)` của tar.bzl 0.10.9 có `include_runfiles`, mặc định `True` khi `mtree = "auto"` (đưa runfiles của mọi `srcs` vào mtree). Binary Go pure, tĩnh, không đọc runfiles lúc chạy → `include_runfiles = False`. Sau khi sửa (arm64): smoke `layer_bytes` 3868624 → 2291152; server binary 20185248, `layer_bytes` 20903376; worker binary 2687136, `layer_bytes` 3405264 — đều ≈ binary (nén gzip) + base distroless ~0.7 MiB, `layers = 13` (12 base + 1). Layer cuối chỉ còn `app`, `app/<name>`.
- **Bẫy / lưu ý**: Không đo bằng mắt: đọc OCI layout (`index.json` → manifest → config/layers) và liệt kê entry layer cuối bằng `tarfile`. `bazel cquery --output=files` cho host, `--config=linux-arm64` và `--config=linux-amd64` trả **cùng** đường dẫn `bazel-out/darwin_arm64-fastbuild/...` (Bazel 8 không tách output theo `--platforms`) → muốn so hai arch phải build rồi copy ra chỗ khác ngay sau mỗi lần build.
- **Code**: [tools/rules/com_tm_container.bzl#L96-L110 — tar(..., include_runfiles = False)](../../../../server/tools/rules/com_tm_container.bzl#L96-L110)
- **Tham khảo**: [tar.bzl — tar macro](https://github.com/bazel-contrib/tar.bzl/blob/main/docs/tar.md)

## Worker skeleton: `run(ctx, log, sigs) int` tách khỏi `main`, không kéo pgx/http
- **Chủ đề**: `go/signal`, `go/slog`, `go/testing`, `go/package-layout`
- **Bối cảnh**: Macro chỉ sinh image từ một `go_binary`, và docs đã mô tả `go run ./services/core/cmd/worker` nhưng binary chưa có. Job thật (hết hạn hold, outbox relay) thuộc P4-T08/P6-T01.
- **Cách làm & lý do**: `main` chỉ tạo logger JSON, `signal.Notify(sigs, SIGTERM, Interrupt)` rồi `os.Exit(run(...))`. `run` log dòng khởi động, `select` giữa `sigs` và `ctx.Done()`, log `shutdown_step` `signal` → `done` kèm `exit_code` — cùng key/giá trị với core server (P0-T09) để một truy vấn log dùng chung. Không dùng lại code `cmd/server` (package `main`, kéo `net`, pgx); cũng không tách package chung chỉ cho hai hằng số — khi worker có job thật (errgroup, hạn dừng) sẽ cân nhắc lại. `go list -deps` không có `pgx`, `net/http`, `redis`: binary 2.7 MiB so với server 20 MiB.
- **Bẫy / lưu ý**: Test đọc log từ goroutine khác → `bytes.Buffer` phải bọc mutex (`-race`). Test "chưa có tín hiệu thì chưa trả về" chờ dòng khởi động trước rồi mới gửi tín hiệu. Test tín hiệu thật dùng `syscall.Kill(os.Getpid(), SIGTERM)` sau khi đã `signal.Notify`, nếu không test process bị giết. Trong container binary là PID 1: không có handler thì SIGTERM bị kernel bỏ qua và `docker stop` phải chờ hết `-t` rồi SIGKILL (exit 137) — ở đây `after≈0.15s`, exit 0.

## Chạy image core cạnh stack compose và kiểm kết quả thật
- **Chủ đề**: `docker`, `docker/compose`, `otel/collector`
- **Bối cảnh**: Compose không có service core (task sau), nhưng image phải chứng minh chạy được với PG và otel-collector.
- **Cách làm & lý do**: Compose không khai báo `networks` → mạng mặc định `snaptix_default`; `docker run --network snaptix_default` dùng được hostname `postgres-core`, `otel-collector:4318`. Publish `127.0.0.1:18080:8080` để không đụng core chạy trên host. Đã kiểm: `/readyz` 200, trace `GET /readyz` + span `pool.acquire`/`connect` (`db=postgresql`, `service.version=dev` vì binary Bazel không có version module) lên Tempo; thiếu `CORE_DATABASE_URL` → `exited exit=1` với log ERROR; `docker stop -t 10` với `CORE_SHUTDOWN_TIMEOUT=3s` → dừng trong 0.15 s, exit 0, chuỗi `signal http_stopped pool_closed done`.
- **Bẫy / lưu ý**:
  - `docker stop -t` phải > `CORE_SHUTDOWN_TIMEOUT` + 1 s (hạn HTTP + tối thiểu 1 s đóng pool/flush), nếu không SIGKILL giữa chừng; mặc định 10 s → `-t 12`.
  - Kiểm distroless/non-root: `docker run --entrypoint /bin/sh` và `docker exec ... /bin/sh` đều exit 127; `docker top` cho uid `65532`.
  - zsh: `$SL:server_docker` bị hiểu là modifier `:s` (substitute) của zsh → nhãn Bazel hỏng (`//ser_dockices/...`). Dùng `${SL}:server_docker` hoặc chạy script bằng bash.
