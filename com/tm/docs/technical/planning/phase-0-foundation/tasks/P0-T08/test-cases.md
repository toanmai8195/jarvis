# Test cases — P0-T08: Middleware: request ID, recover, access log, OTel HTTP

> **Phạm vi**: chuỗi middleware HTTP cho core, bọc router chi của P0-T07. Gồm bốn phần: **request ID** (sinh hoặc nhận từ client, trả trong header response, đặt vào context và vào mọi dòng log của request), **recover** (panic trong handler thành 500 theo format lỗi của api.md, process vẫn sống), **access log** (mỗi request một dòng JSON slog), **OTel HTTP** (span server và metric `http.server.request.duration` theo route pattern, đọc `traceparent`). Căn cứ:
> - Phase 0 README: dòng P0-T08. **P0-NFR1** "Log dạng JSON, có `trace_id`, `request_id`". **P0-NFR2** "Trace truyền từ `bff` sang `core` qua `traceparent`". Challenge **G10** "OpenTelemetry trace, slog JSON, Prometheus metrics". DoD "Gọi `bff /healthz?deep=1` → thấy **một trace** gồm span của bff và core", nên `/healthz` của core **phải** có span.
> - [acceptance-tests](../../acceptance-tests.md) **P0-AT06**: "Log JSON có `trace_id`, `request_id`, `status`, `latency_ms`". Tên field trong access log lấy theo AT này.
> - [api.md](../../../../api.md): mục "Quy ước chung" (JSON `snake_case`, header `traceparent`) và mục "Lỗi" (`{"error":{"code","message","details"}}`).
> - [architecture](../../../../architecture.md) mục Observability: log "luôn kèm `trace_id`, `user_id`, `request_id`". Dashboard RED dùng metric OTel `http.server.request.duration` (Prometheus: `http_server_request_duration_seconds_*`), lọc theo label `http_route`. Luồng "app → OTLP → otel-collector → Tempo / Prometheus".
> - [project-structure](../../../../project-structure.md): `services/core/internal/httpx/` = "router, middleware, map lỗi → HTTP". Quy tắc 3 tầng: đưa vào `pkg/` chỉ khi "service thứ hai cần". `pkg/otelx/` ("tracing, metrics, slog") là việc của P0-T10.
> - Phase 0 README: **P0-T10** "Tích hợp OpenTelemetry SDK trong `pkg/otelx`, export OTLP". **P0-T09** graceful shutdown. **P0-T12** trace xuyên bff → core.
> - [execute-all-notes](../../../execute-all-notes.md) mục P0-T07, handbook P0-T06/P0-T07: core đang có hai nguồn metric là scrape `/metrics` (`job="core"`) và OTLP (`job="snaptix/core"`, từ P0-T10). "P0-T08/P0-T10 nên chọn một nguồn cho metric RED."

> **Giả định** (reviewer xem kỹ):
> - A1. **Vị trí**. Middleware nằm trong `services/core/internal/httpx/` (một hoặc vài file, ví dụ `middleware.go`), hoặc package con `services/core/internal/httpx/<tên>`. **Không** đặt vào `pkg/`: hiện chỉ core có HTTP server Go (stats-worker là worker, bff là Node), nên chưa có "service thứ hai cần". Không tạo `pkg/otelx` (P0-T10). Tên hàm/type do người làm chọn. Không `IFoo`/`FooImpl`, không `utils`/`common`.
> - A2. **Header request ID** là `X-Request-ID`. Docs chưa nêu tên, đây là tên phổ biến và BFF (P0-T11/T12) sẽ dùng cùng tên. HTTP không phân biệt hoa thường, Go chuẩn hoá thành `X-Request-Id`, nên TC so khớp không phân biệt hoa thường. Bước 5 phải thêm dòng `Request ID | Header X-Request-ID` vào bảng "Quy ước chung" của api.md (TC24).
> - A3. **Định dạng request ID**:
>   - Nhận giá trị client gửi khi khớp `^[A-Za-z0-9._:-]{1,128}$`.
>   - Giá trị rỗng, dài hơn 128 ký tự, hoặc có ký tự ngoài tập trên (khoảng trắng, `<`, `"`, non-ASCII...) thì **thay bằng ID mới**, không trả 400. Lý do: request ID dùng để truy vết, không được làm hỏng request; và không để client đưa chuỗi tuỳ ý vào log.
>   - ID tự sinh là UUID dạng chữ thường 36 ký tự, khớp `^[0-9a-f]{8}-[0-9a-f]{4}-[47][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. Khuyến nghị v7 theo quy ước ID của dự án, v4 cũng được.
>   - Có hàm export để đọc ID từ `context.Context` (ví dụ `httpx.RequestIDFrom(ctx)`).
> - A4. **Log theo context**. Logger của core bọc `slog.Handler` bằng một handler lấy `request_id` (và `trace_id`, `span_id` khi span context hợp lệ) từ `ctx`. Nhờ đó **mọi** lời gọi `log.*Context(r.Context(), ...)` trong request đều có `request_id`, kể cả dòng WARN có sẵn của `/readyz`. Log ngoài request (khởi động) không có key `request_id`, hoặc có nhưng rỗng.
> - A5. **Access log**. Mỗi request đúng **một** dòng JSON, ghi sau khi handler xong, gồm các field:
>
>   | Field | Kiểu | Ý nghĩa |
>   |---|---|---|
>   | `method` | string | `GET`... |
>   | `route` | string | Route pattern của chi, ví dụ `/readyz`. Không khớp route (404) thì rỗng hoặc vắng, **không** phải path thô |
>   | `path` | string | `URL.Path`, **không** kèm query string |
>   | `status` | number | Mã trạng thái thật đã trả (kể cả 404/405/500) |
>   | `latency_ms` | number | ≥ 0 |
>   | `bytes` | number | Số byte body đã ghi |
>   | `request_id` | string | Bằng giá trị header response |
>   | `trace_id` | string | 32 hex, có khi span context hợp lệ |
>
>   Dòng access log được nhận diện bằng key `latency_ms`. `msg` do người làm chọn.
>   - Mức log: status < 500 là `INFO`, ≥ 500 là `WARN` hoặc `ERROR`.
>   - Log **mọi** route, kể cả `/healthz`, `/readyz`, `/metrics`. Docs không yêu cầu bỏ qua, và hiện chỉ có ba route này để chạy P0-AT06.
>   - Không log header nào, trừ `User-Agent` nếu muốn. Tuyệt đối không log `Authorization`, `Cookie`, `X-Api-Key`, và không log query string.
> - A6. **Recover**. Handler panic thì trả `500`, `Content-Type: application/json`, body `{"error":{"code":"INTERNAL","message":"<thông báo chung>"}}`.
>   - api.md chưa có dòng cho 500. Mã `INTERNAL` là giả định, bước 5 thêm dòng `500 | INTERNAL` vào bảng lỗi của api.md.
>   - Body **không** chứa giá trị panic hay stack.
>   - Log một dòng mức `ERROR` có `request_id`, giá trị panic (ví dụ key `panic`) và stack (ví dụ key `stack`, chứa tên file `.go` và tên hàm handler).
>   - `http.ErrAbortHandler`: panic lại (re-panic) để `net/http` cắt kết nối như thiết kế. Không ghi 500, không log ERROR kèm stack. Đây là hành vi của `net/http` và `chi/middleware.Recoverer`.
>   - Panic sau khi handler đã gửi header: không gọi `WriteHeader` lần hai. Vẫn log ERROR. Access log ghi status đã gửi.
> - A7. **OTel HTTP** chỉ dùng **API** OTel (`go.opentelemetry.io/otel`, `.../trace`, `.../metric`, `.../propagation`). `go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp` được phép. Code không phải test **không** import `go.opentelemetry.io/otel/sdk/...` hay `.../exporters/...` (P0-T10).
>   - Middleware nhận `TracerProvider`, `MeterProvider`, `TextMapPropagator` qua tham số/option. `main` truyền bản global (`otel.GetTracerProvider()`...), P0-T10 sẽ cấu hình bản global.
>   - Unit test inject SDK in-memory: `sdk/trace` + `sdk/trace/tracetest.SpanRecorder` (hoặc `InMemoryExporter`), `sdk/metric.NewManualReader`, `propagation.TraceContext{}`. SDK chỉ xuất hiện trong `_test.go` (và `go.mod`, `go_test` deps).
>   - Tên span theo semconv: `"<METHOD> <route>"`, ví dụ `GET /readyz`. Không khớp route thì chỉ `"<METHOD>"`, **không** chứa path thô. Span kind `Server`. Có thuộc tính `http.request.method`, `http.route` (khi có route), `http.response.status_code`. Status `Error` khi 5xx, `Unset` khi 4xx (semconv cho server span).
>   - Metric `http.server.request.duration`, kiểu histogram, đơn vị `s`. Thuộc tính gồm `http.request.method`, `http.response.status_code`, `http.route` (khi có). **Không** có `url.path`, `url.full`, `url.query`, `http.target`, `user_agent.original`, `client.address`. Nhờ vậy số chuỗi thời gian không tăng theo path thô hay giá trị tham số.
>   - Route pattern chỉ biết **sau** khi chi định tuyến. Middleware bọc ngoài router phải đọc `chi.RouteContext(ctx).RoutePattern()` sau `next.ServeHTTP` để đặt tên span và thuộc tính (ví dụ `otelhttp.WithSpanNameFormatter` không đủ, cần `span.SetName` + `otelhttp.Labeler`/`WithMetricAttributesFn`, hoặc tự viết). Người làm chọn cách, TC chỉ kiểm hành vi.
> - A8. **Chọn nguồn metric RED** (execute-all-notes P0-T07): metric RED chỉ đi qua OTel (OTLP từ P0-T10, `job="snaptix/core"`, khớp dashboard P0-T06). Task này **không** đăng ký histogram `prometheus/client_golang` cho request. `/metrics` (job `core`) chỉ giữ metric runtime Go/process. Vì trước P0-T10 MeterProvider global là no-op, metric RED **chưa** xuất ra Prometheus ở task này. Việc đó kiểm ở P0-T10. Ghi quyết định vào handbook P0-T08 và execute-all-notes.
> - A9. **Thứ tự middleware**: TC không bắt một thứ tự cụ thể mà kiểm hệ quả (TC21). Khi handler panic:
>   - response vẫn có `X-Request-ID`;
>   - access log ghi `status` 500, cùng `request_id` với dòng log panic;
>   - span có status `Error`, `http.response.status_code=500`;
>   - metric ghi một điểm với status `500`;
>   - `trace_id` của access log bằng trace ID của span.
>
>   Muốn vậy thì request ID và OTel phải bọc ngoài access log, access log bọc ngoài recover, recover bọc ngoài router.
> - A10. **Không kiểm trên Tempo/Prometheus thật**: exporter OTLP và SDK là P0-T10, trace xuyên bff → core là P0-T12. Trước P0-T10, provider global là no-op, nên log lúc chạy thật có thể **không** có `trace_id`. `trace_id` trong log được kiểm bằng unit test (TC19). P0-AT06 để ⬜ tới P0-T10.

Góp ý không chặn:
1. A7 (dòng cuối) ghi "Middleware bọc ngoài router phải đọc `chi.RouteContext(ctx)`" — người làm lưu ý: phải gắn qua `r.Use(...)` trên mux gốc, hoặc tự đặt `chi.NewRouteContext()` vào ctx trước khi gọi mux (chi dùng lại rctx có sẵn); nếu không sẽ panic nil/route rỗng. 404/405 vẫn đi qua middleware của `r.Use`.
2. TC19/TC20/TC21 cần route tham số và handler panic "chỉ trong test" nhưng TC21 bắt dùng **cùng hàm dựng** với `main` và TC23 cấm route debug ở code chạy thật → hàm dựng nên nhận thêm tuỳ chọn đăng ký route (hàm không export hoặc option) để test gắn route riêng.
3. TC04 `grep -cE 'opentelemetry_go_otel_sdk|otel_exporters'`: nếu phiên bản `otelhttp` được chọn kéo `otel/sdk` vào deps non-test thì TC04 fail — kiểm ngay khi chọn phiên bản; nếu vướng thì tự viết middleware bằng OTel API (A7 cho phép).
4. TC06 `grep -v router.go | head -1`: nếu có nhiều file middleware, `F` có thể là file khác file mong muốn — bất kỳ file non-test nào trong package đều đủ cho query `rdeps`, không ảnh hưởng kết quả.
5. TC15: `xargs -P 20` ghi header của nhiều `curl` vào cùng pipe; mỗi dòng header là một lần `write` nhỏ (< PIPE_BUF) nên thực tế không xen dòng, nhưng nếu `wc -l` lệch thì chạy lại với mỗi curl ghi ra file riêng trước khi kết luận fail.
